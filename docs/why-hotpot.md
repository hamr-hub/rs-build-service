# Hotpot 的价值与意义

> 这份文档回答三个问题：**它解决谁的什么问题**、**为什么用 Rust 做**、
> **和现有方案差在哪**。想直接上手请看[入门说明](getting-started.md)。

---

## 1. 它要解决的真问题

Rust 的编译等待是**真实的生产力损耗**，而不是「感觉有点慢」：

- 中等规模项目（200+ 依赖）干净构建动辄 5–20 分钟，其中绝大部分花在
  **重复编译同样的第三方依赖**上——换台机器、换个 CI runner、换个分支，全都重来一遍；
- 团队里每个人、每台机器都在**各自为战**地编译同一批 crate。本地缓存换个
  机器就失效，CI 缓存换个 job 也失效；
- 容器镜像构建慢：Docker 层缓存很脆弱，`Cargo.lock` 任意一行变动就全量重编；
- 部署重、迭代慢：Rust 没有稳定 ABI，做不到 Node 那种保存状态的热重载，
  静态二进制 + 滚动重启意味着每次发布都要经历一次连接抖动。

Hotpot 的判断是：**这些不是四个独立问题，而是同一个问题的四个面——
「构建」在 Rust 生态里从来没有被当成一种可以被复用、可以被服务化的资源。**

## 2. 它是什么

一句话：**开源、可自托管的 Rust 构建服务**，把构建从「每个人本地跑一遍」
变成「一项可以远程提交、共享缓存、零停机上线的基础设施」。

由一个服务端和若干客户端组件组成：

| 能力 | 说明 |
|------|------|
| 远程构建 | HTTP API + CLI 提交，SSE 实时日志，取消、产物下载 |
| 多级内容寻址缓存 | 依赖层（CARGO_HOME）→ crate 层（sccache 协议）→ 产物层（blake3 CAS） |
| 双协议缓存服务 | 对外同时提供 sccache（WebDAV 兼容）与 Turborepo v8 端点 |
| 工具链选择 | 每个构建可指定 `stable` / `nightly-2026-01-15` / `1.98.0`，容器镜像自动匹配 |
| 本地热重载 | `hotpot-dev`：保存即增量重建，构建失败保留旧进程，重启窗口不拒连 |
| 零停机部署 | `hotpot-agent`：supervisor 常驻持有 listen socket，失败自动回滚 |
| 容器化执行 | 构建跑在工具链容器内，与服务环境隔离 |
| 可观测 | `/metrics` 暴露构建状态分布、队列深度、阶段耗时、**缓存命中率** |

## 3. 为什么用 Rust 写它

这不是「用自己擅长的语言写」，而是**语言特性恰好对应这个问题的核心矛盾**：

| 矛盾 | Rust 的答案 |
|------|------------|
| 缓存服务要在高并发下稳定，延迟抖动直接影响构建体验 | 无 GC 的 `tokio` + 无锁原子计数；命中率计数是 `AtomicU64` 的 `fetch_add`，没有锁竞争 |
| 构建是 IO 密集（子进程、HTTP、磁盘）但夹杂 CPU 密集（哈希、压缩） | `async` 处理 IO 等待，`blake3`（SIMD）处理哈希，两者不互相阻塞 |
| 产物可能几百 MB，必须避免「为了算哈希先读进内存」 | 内容寻址天然是流式的；CAS 用临时文件 + 原子 `rename`，崩溃不留半截文件 |
| 跨平台自托管（macOS/Linux、x86/ARM） | 一个静态二进制 + `docker compose up`，没有运行时依赖 |
| 进程级零停机切换需要精确的 fd 交接 | `AF_UNIX` / `SCM_RIGHTS` 是系统调用级的原语，Rust 侧只有 `unsafe` 一小块，能被审干净 |
| 要被当作可信基础设施部署 | 无 `unsafe` 的热路径、类型系统表达的领域模型（`BuildStatus` 状态机、`SourceSpec` tagged union），把「非法状态」挡在编译期 |

一个具体的例子说明这不是修辞：调度器的「原子认领」只用了**一条** SQL——
`UPDATE … WHERE id = (SELECT … LIMIT 1) RETURNING *`，靠 SQLite 的写锁
天然实现互斥。用 Go/Java 写同样的逻辑，要么多一次往返，要么自己实现
分布式锁；而「租约过期接管」（worker 失活后任务重新入队）只是
`leased_until_ms < now` 一个条件。**这类「用对原语就不需要代码」的地方，
正是系统类服务用 Rust 写的回报。**

## 4. 和现有方案的区别

| 方案 | 覆盖 | 缺口 |
|------|------|------|
| `cargo` + `sccache` 本地 | crate 级缓存 | 换机器即失效；无远程构建；无部署能力 |
| GitHub Actions + 缓存 | CI 加速 | 只在 CI 内有效；本地开发依旧全量编译；与部署无关 |
| Bazel / Remote Execution (REAPI) | 极致缓存与并行 | 心智负担与接入成本极高；Rust 生态需要额外规则文件；不解决部署 |
| Turborepo Remote Cache | 前端 monorepo 缓存 | 与 Rust 无关；纯缓存，不构建、不部署 |
| Docker BuildKit 缓存 | 镜像层复用 | 层缓存脆弱，锁文件变动即失效；无增量、无实时日志、无零停机 |
| Nginx + 一堆脚本 | —— | 拼装起来通常止步于「能跑」，没有状态机、回滚、租约、协议兼容 |

Hotpot 的定位是**把这些能力装进一个二进制**，并且**诚实地划定边界**：
它不是通用 CI，不追求替代 GitHub Actions；它不承诺任意 Rust 程序的内存级
热升级（Rust 没有稳定 ABI，工程上不可行），而是提供**显式约定的进程级切换**。

## 5. 真正的价值：缓存协议的双向复用

这是 Hotpot 最有杠杆的一处设计。

大多数项目把「远端缓存」当成一个**对外功能**（我要让别人能用我的缓存）。
Hotpot 反过来做了两件事：

1. **对外**：实现 sccache（WebDAV 兼容）与 Turborepo v8 两套协议，
   于是 Hotpot 立刻成为前端 monorepo 和 C/C++ 项目也能用的缓存后端
   ——**同一份存储服务两类生态**；
2. **对内**：让 Hotpot **自己的构建**通过自己的 sccache 端点走远端缓存
   （`--self-sccache`）。缓存协议从「一个功能」变成「自己也在吃的狗粮」。

第 2 点是关键：它意味着协议实现的正确性每天都被自己的构建验证一次，
而不是躺在集成测试里。这也解释了为什么实测里能做到
「清空本地盘、只用远端，89 个 crate 100% 命中」。

详见 [双协议缓存说明](protocols/README.md)。

## 6. 对不同人的价值

| 你是谁 | 收益 |
|--------|------|
| **单人 / 小团队** | `docker compose up -d` 就得到远程构建 + 共享缓存 + 零停机部署，零外部依赖（SQLite + 本地盘） |
| **CI 维护者** | 把 `sccache` / `turbo` 的远端指向 Hotpot，`/metrics` 给出可量化的命中率与阶段耗时 |
| **平台团队** | 协议兼容意味着不必为每个生态各搭一套缓存；`/v1/toolchains` 与显式工具链选择让「多工具链矩阵构建」可编排 |
| **Rust 布道者** | 一个可读、可改、可贡献的完整系统：9 个 crate，职责清晰，没有隐藏的分布式魔法 |
| **想学系统设计的人** | 内容寻址、租约与失活接管、状态机与 point-of-no-return、fd 交接、协议兼容——都在一个能跑起来的仓库里，且每个取舍都写在文档里 |

## 7. 它诚实的边界

写下来是为了让评估更快：

- **API 无鉴权**（构建侧）；缓存端点可用 `HOTPOT_CACHE_TOKEN` 启用 Bearer。
  对外暴露必须前置反向代理。
- **git 来源构建会执行不可信代码**（`build.rs`/proc-macro），因此**默认关闭**，
  需显式 `--allow-git-source`。
- **构建隔离**在 local 模式下等于没有（build.rs 可以执行任意代码）；
  docker 模式提供容器边界，但仍共享 daemon socket。
- **缓存条目不做签名校验**：sccache 靠 ZIP CRC32，turbo 的 HMAC 由客户端
  校验。恶意服务端可以投毒——所以缓存端点不应暴露到不可信网络。
- **artifact 暂不流式传输**：整块进内存，受 4 GiB 上限保护。
  超大 artifact 场景是明确的下一个优化点。
- **单机形态优先**：Postgres / S3 / K8s 演进路径写在架构文档里，但未接线。

## 8. 一句话总结

> **让 Rust 项目的构建，第一次成为一种可以被复用、被观测、被服务化的资源。**
