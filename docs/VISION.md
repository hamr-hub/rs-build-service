# Hotpot —— Rust 项目的快速构建与热部署服务

> 「一锅热乎的 Rust 构建」—— 让 Rust 项目像脚本语言一样快速迭代，
> 像静态语言一样高性能交付。

## 1. 我们要解决什么问题

Rust 以「编译慢」闻名，尤其在以下场景中痛点突出：

1. **CI / 打包流水线慢**：一个中等项目（200+ 依赖）干净构建动辄 5–20 分钟，
   其中绝大部分时间花在第三方依赖的重复编译上。
2. **团队成员各自为战**：每个开发者、每台 CI 机器都在重复编译同样的依赖；
   本地缓存换台机器就失效。
3. **容器镜像构建慢**：Docker 层缓存脆弱，`Cargo.lock` 任意变动就全量重编。
4. **部署重、迭代慢**：静态二进制 + 滚动重启让 Rust 服务无法像 Erlang/OTP
   那样热升级，也无法像 Vite/Node 那样保存状态热重载，开发体验与
   Java/Go/JS 生态存在代差。
5. **没有统一的构建服务**：Java 有 Bazel/远程执行，JS 有 Turborepo Remote
   Cache + Vite HMR，C/C++ 有 distcc/sccache——而 Rust 生态缺少一个
   **开箱即用、可自托管、同时覆盖「远程缓存构建」与「热部署」**的服务。

## 2. Hotpot 是什么

Hotpot 是一个**开源、可自托管的 Rust 构建服务**，由一个服务端
（API + 调度 + 分布式缓存）和若干客户端组件（CLI / worker / 热重载库）组成：

- **远程构建**：通过 HTTP API 或 CLI 提交构建（Git 仓库或源码包），
  服务端调度 worker 执行，实时流式返回日志与进度。
- **多级内容寻址缓存**：依赖层（cargo-chef 风格）→ crate 编译产物层
  （sccache 兼容）→ 最终产物层，全部以输入指纹为 key，跨构建、跨用户共享。
- **增量构建**：worker 复用预热的 registry/git/target 缓存，只编译变化部分；
  构建以秒级而非分钟级完成。
- **热部署**：
  - 开发态：`hotpot dev` 监听源码变化，热重载动态库（保留应用状态）；
  - 生产态：`hotpot deploy` 通过 fd 传递 + 优雅停机实现**零停机二进制切换**，
    不掉连接。
- **单二进制自托管**：一个 `hotpot-server` 加本地磁盘即可服务小团队；
  也可水平扩展为多 worker + 对象存储的集群形态。

## 3. 设计目标与非目标

### 目标

| 维度 | 目标 |
|------|------|
| 构建延迟 | 预热缓存下，典型项目增量构建 P95 < 30s；冷构建比裸 cargo 快 5–20 倍 |
| 缓存命中率 | 稳定依赖项目的 CI 缓存命中率 > 95%（按编译耗时加权） |
| 部署停机 | 生产热切换 TCP 连接 0 丢失；开发热重载 < 2s |
| 易用性 | `cargo install hotpot-cli` + 一条命令启动服务；客户端零配置接入 |
| 可移植 | macOS (aarch64/x86_64)、Linux (glibc/musl) 开发与构建；容器化部署 |
| 安全性 | 构建沙箱隔离、租户缓存隔离、产物可追溯（provenance） |
| 可观测 | 构建各阶段耗时分解、命中率、队列延迟，内置 OpenTelemetry |

### 非目标（至少在早期）

- 不做通用 CI（不试图替代 GitHub Actions / Drone 的流水线编排），
  Hotpot 是**构建加速与部署服务**，可被 CI 调用。
- 不做跨语言构建（不编译 C++/Java 项目），但允许通过 build script
  与 C 依赖共存。
- 不追求 100% 透明的任意 Rust 程序内存级热升级——Rust 没有稳定 ABI，
  通用函数级热替换在工程上不可行；我们提供**显式约定的热重载接口**。
- 不自建分布式数据库/消息队列等重型基础设施，小团队形态保持零外部依赖。

## 4. 形态总览

```
   开发者 / CI                    生产目标机器
  ┌──────────┐                 ┌──────────────────┐
  │ hotpot   │  build/deploy   │ hotpot-agent     │
  │ CLI      │──────────────▶  │ (fd 传递监管者)  │
  └──────────┘                 └──────────────────┘
        │                              ▲
        │ HTTP/gRPC + 流式日志          │ 拉取/接收新二进制
        ▼                              │
  ┌─────────────────────────────────────────────────┐
  │                 hotpot-server                   │
  │  API  ──  Scheduler/Queue  ──  Workers          │
  │                    │                            │
  │                    ▼                            │
  │        内容寻址缓存 (本地磁盘/S3/兼容 sccache)  │
  └─────────────────────────────────────────────────┘

  开发态: hotpot dev → watchexec + hot-lib-reloader (动态库热替换, 状态保留)
```

## 5. 开源规划

- 协议开放：缓存协议同时兼容 sccache client 协议（可直接用 `RUSTC_WRAPPER`
  接入现有 CI），自有 API 提供 JSON Schema。
- 双协议许可：MIT OR Apache-2.0（Rust 生态惯例）。
- 分期交付：MVP（单节点构建+缓存）→ 多 worker → 热部署 → 云原生/ provenance。
- 调研先行：所有设计决策基于对 Bazel REAPI、Buck2、sccache、Erlang relup、
  Vite HMR、Firecracker 等成熟系统的调研，见 `docs/research/`。
